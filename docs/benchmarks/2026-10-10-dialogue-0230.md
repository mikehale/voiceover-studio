## Method and reproducibility

The source was first cut precisely to 150–160 seconds with bundled FFmpeg (`-ss 150 -t 10`, H.264 `libx264`, preset `fast`, CRF 18, two encoding threads, AAC 192k). This preparation is excluded from timing. Re-encoding avoids the extra lead-in from stream-copy keyframe alignment.

The bundled `voiceover-studio process` command ran on that exact clip with a new work directory, `--device cpu --jobs 2 --tts-jobs 1 --min-lines-per-min 0 --video-codec copy --metrics-json pipeline.json`. No SRT was supplied: OCR read the actual subtitles. The app's saved voice map selected `bm_lewis` for the two cyan narration lines. The short-sample line-count guard was disabled; the actual two recognized lines were verified afterward.

The bundled benchmark supervisor (`voiceover_studio.benchmark.supervise`) launched the CLI in a new process group and sampled memory from launch through exit. Limits were 8 GiB system swap, 24 GiB process-group RSS, 15% free memory and ten minutes. No guard fired. The per-stage timings exclude launcher/supervisor overhead; the total monitored time includes it.

This used a fresh pipeline cache, but did not flush OS file or Python bytecode caches. Another full-episode job and its clone worker were active, so treat this as a functional baseline with recorded background load, not a controlled speed comparison. System swap was already allocated before this run and did not grow. RSS is not a measurement of all GPU/driver allocations. This standard-voice sample does not establish clone speed or long-run memory stability.
